### DB 이전 (2026-11-16): Supabase(PostgreSQL + pgvector) → Google Cloud Firestore

**왜**: 웹 사이트가 가끔 DB를 못 불러왔습니다. 확인해 보니 Supabase DB가 **싱가포르**(`ap-southeast-1`)에 있어 서울 Cloud Run과 멀었고(연결 약 1.4초 · 왕복 약 80ms), 세션 모드 풀러라 동시 연결 수 한도(약 15)에 걸릴 수 있었습니다. Cloud Run과 같은 GCP 프로젝트(`qupict`)의 Firestore로 옮겼습니다.

- **위치**: Firestore `(default)` DB, 서울 `asia-northeast3`, Native 모드 · Standard. 연결 개념이 없어 동시 연결 한도가 없고, 1주일 안 쓰면 멈추는 일도 없습니다
- **속도 (측정 2026-11-16, 로컬 → 서울)**: 문서 읽기 왕복 약 66ms, 벡터 검색 1번 약 0.1~0.2초
- **비용**: 무료 한도 하루 읽기 5만 · 쓰기 2만 · 저장 1GiB (`(default)` DB만). 질문 1번 ≈ 읽기 100~250
- **코드**: `qupict/db.py`를 Firestore로 다시 썼습니다 (함수 이름 · 인자는 그대로). 다른 파일에 흩어져 있던 SQL 조회(현황 · 남은 일 세기 · 많이 보도된 기사 · 실험용 조회 등)도 모두 `db.py` 함수로 옮겼습니다. `schema.sql` · `docker-compose.yml`(로컬 PostgreSQL)은 지웠습니다
- **벡터 검색**: `find_nearest`(코사인, 정확한 KNN). 청크 문서의 `search_keys`(= "topic id:판정")와 발행일로 먼저 거른 뒤 찾습니다. 유사도 = 1 − 거리로 예전 pgvector 값과 같습니다
- **데이터 이전**: `tools/migrate_supabase_to_firestore.py`로 6,355건을 옮겼습니다 (임베딩 그대로, topic id 그대로). **14개 topic 모두 벡터 검색 결과가 예전 DB와 같은 청크 · 같은 순서**(유사도 차 0.0001 이하), 질문 가능 기사 수 · 남은 일 개수도 같음을 확인했습니다
- **바뀐 값**: `image_id`가 숫자 → 문자열(`"기사키/이미지키"`), `.env`의 `DATABASE_URL` → `FIRESTORE_PROJECT=qupict`, 실험 B의 검색 엔진 이름 `pgvector` → `db`
- **로컬 인증**: 조직 정책상 서비스 계정 키(JSON)를 만들 수 없어서 본인 Google 계정으로 로그인합니다 (아래 3-4)
- **배포**: Cloud Run 환경변수에 `FIRESTORE_PROJECT=qupict`, 서비스 계정에 `Cloud Datastore 사용자` 역할 (편집자면 이미 있음). `DATABASE_URL`은 새 코드가 배포된 뒤 지웁니다

### 최신 변경 (2026-11-16): 웹 화면 · 질문 시점 · 배포

**질문은 3번 과정이 모두 끝난 뒤에 답합니다** (`web.py`, `web/app.js`)
- 11-14~15에 넣은 **"저장된 기사로 바로 답하기"(아래 1-0)를 없앴습니다.** 예전에 준비한 검색어·의미여도 3번 카드의 과정(수집 · 필터링 · 인덱싱 · 이미지 글자 읽기)이 **모두 끝난 뒤에** 질문을 받습니다. 첫 답변부터 새로 모은 기사와 이미지 속 글자까지 검색에 들어갑니다.
  - 없앤 것: `web.py`의 `_open_from_db`, 작업 상태의 `early`(먼저 답할 때 쓴 기사 수), 화면의 "DB에 저장된 기사 N건으로 먼저 답합니다" 안내
- **DB 재사용은 그대로입니다.** 이미 판정·인덱싱한 기사는 다시 처리하지 않아서 같은 검색어는 준비가 빠릅니다 (할 일 없는 단계 건너뛰기, 아래 1-0).
  - 측정 (방송인 강남, 30일, 다시 준비): 준비 완료 **3.5초** → 이미지 글자 읽기 끝 **7.6초** → 그때 질문에 답함
- 준비 중에 질문을 적어 두면, 모두 끝나는 대로 적은 순서대로 답합니다.

### 1-0. 최근 변경 (2026-11-14~15): 웹·질문 (교수님 피드백 반영)

**DB 재사용이 화면에서 보이게**
- ~~**저장된 기사로 바로 답하기**: 예전에 준비한 검색어·의미면 수집이 끝나기를 기다리지 않고 DB에 저장된 기사로 바로 질문을 받습니다.~~ **→ 11-16에 없앴습니다.** 지금은 3번 과정이 모두 끝난 뒤에 답합니다 (위 최신).

- **할 일 없는 단계 건너뛰기**: 수집 뒤 판정·인덱싱할 기사 수를 먼저 세고(`pipeline.count_pending`, 약 0.2초), 0건인 단계는 부르지 않습니다. 예전에는 할 일이 없어도 각 단계가 topic 기사 전체(임베딩 포함)를 불러와 1.5초씩 걸렸습니다.
  - 측정 (당근, 같은 검색어 다시): 준비 **20.1초 → 5.2초**
  - "저장 내용을 정리하는 중… (3초)" 대기도 새로 저장한 것이 있을 때만 합니다.
- **화면에 숫자 표시**: 로그 줄마다 시작부터 걸린 시간이 붙고, 준비 완료 때 총 시간을 보여 줍니다. "DB 재사용 N건 + 새로 저장 M건", "새로 판정할 기사 없음 (DB에 저장된 판정 그대로 사용)"이 그대로 보입니다.

**앞 대화 기억**
- 최근 질문·답변 2개를 답변 프롬프트의 `[이전 대화]`와 검색 문장 만들기(HyDE·Multi-Query)에 넣습니다. LLM 호출 수는 그대로입니다 (`qa.history_text`, `retrieval.search_topic(history=)`).
  - 예 (방송인 강남): "와이프가 누군데?" → 이상화 / 이어서 "그 사람 직업은 뭐야?" → **이상화**의 직업으로 답함 (예전에는 강남으로 받아들임)
- 첫 질문에 검색어가 없으면 질문 앞에 검색어를 붙여 검색합니다 (LLM 없이, `retrieval.with_subject`). 예: "최근 근황은?" 유사도 0.24 → "강남 최근 근황은?" 0.52
- 남은 한계: "와이프가 누군데?"처럼 근거 유사도가 기준값 0.5 근처(0.46~0.54)인 질문은 실행마다 근거를 찾기도 하고 못 찾기도 합니다 (10장 "유사도 기준 0.5").

**1단계 멈춤 수정**
- 네이버 검색 요청에 제한 시간이 없어 aiohttp 기본값 300초를 썼습니다. 네이버가 한 요청에 답하지 않으면 화면이 "[1단계] 검색어 → …"에서 5분 넘게 멈췄습니다 (재시도 3번이면 최대 약 15분).
- 요청마다 **10초 제한**(`collect.SEARCH_TIMEOUT_SECONDS`)을 걸었습니다. 응답 없는 검색어만 빼고 나머지 결과로 계속합니다 (최대 약 35초).

**많이 보도된 기사 Top 5 (`qupict/hot.py`)**
- 웹 화면의 3번(수집·필터링)과 4번(질문하기) 사이에 나옵니다. 중복(비슷한 기사)이 가장 많이 묶인 대표 기사 5건의 제목(원문 링크) · 한 줄 요약 · 언론사 · 날짜 · 비슷한 기사 수입니다. 질문 칸처럼 준비 시작 때 카드가 미리 열립니다.
- **한 줄 요약에 LLM을 쓰지 않습니다.** 대표 기사 앞 5문장 중에서 같은 묶음의 다른 기사들도 쓴 명사(Kiwi)를 가장 많이 담은 문장을 고릅니다. Top 5 전체에 흔한 단어(검색어 등)는 IDF로 낮춥니다.
  - 기사에 실제로 있는 문장 그대로라 지어낸 내용이 없고, 같은 입력이면 항상 같은 결과입니다.
  - 측정: 실제 DB 5개 topic에서 LLM 호출 0번, 요약 0.6~0.7초 (서버에서 처음 한 번 Kiwi 로딩 약 1.8초)
  - 고를 문장이 없으면(라디오 대본 등) 요약을 비우고 제목·링크만 보여 줍니다.
- 웹 화면의 고정 첫 질문(수집된 기사 전체 요약, LLM)은 없앴습니다. 터미널(`run.py`)은 그대로입니다.

### 1-1. 최근 변경 (2026-11-14~15): 중복 제거

**중복 제거 기준 (`qupict/filtering.py`)**

| 기준 | 비교하는 것 | 임계값 (`.env`) |
| --- | --- | --- |
| `title` | 제목 임베딩 | `DEDUP_TITLE_THRESHOLD` |
| `content` | **검색어가 들어간 문단** 임베딩 (예전: 본문 앞 5문장) | `DEDUP_CONTENT_THRESHOLD` |
| `noun` | 제목의 드문 고유명사 겹침 (TF-IDF) | `DEDUP_NOUN_THRESHOLD` |
| `jaccard` | **새로 추가.** 제목 + 검색어 문단의 글자 3-gram 자카드 (복붙·통신사 기사용) | `DEDUP_JACCARD_THRESHOLD` |

- 기본값은 `DEDUP_BY=all`(넷 다)와 `DEDUP_RULE=2`입니다. **기준 넷 중 2개 이상**이 임계값을 넘어야 중복입니다.
- **11-15 변경: "하나만 넘어도 중복" → "4개 중 2개 이상 넘어야 중복"**
  - 이유: `or`(하나만 넘어도 중복)일 때 삼전 검색에서 관련 없는 기사까지 묶였습니다.
  - `DEDUP_RULE`에 숫자 k를 쓸 수 있게 했습니다: `and`(전부) / `or`(1개) / k(k개 이상). k가 기준 수보다 크면 기준 수로 줄입니다 (예: `DEDUP_BY=title,content`에 k=5 → `and`와 같음).
  - 임계값도 올렸습니다.

    | 설정 | 전 | 후 |
    | --- | --- | --- |
    | `DEDUP_TITLE_THRESHOLD` | 0.7 | 0.8 |
    | `DEDUP_CONTENT_THRESHOLD` | 0.7 | 0.8 |
    | `DEDUP_NOUN_THRESHOLD` | 0.3 | 0.4 |
    | `DEDUP_JACCARD_THRESHOLD` | 0.5 | 0.6 |
    | `DEDUP_PASSAGE_WINDOW` (검색어 문단 폭) | ±1문장 | ±2문장 |
    | `DEDUP_RULE` | `or` | `2` |

  - 아직 새 설정으로 삼전·강남·서울여대를 다시 확인하지는 않았습니다 (`check_dedup.py`로 확인 필요).
- **중복 제거에는 LLM을 쓰지 않습니다.** `title`·`content`는 임베딩 모델(`text-embedding-3-small`)로 글을 벡터로 바꾸기만 하고, `noun`(kiwipiepy)·`jaccard`(글자 계산)는 외부 호출 없이 로컬에서 계산합니다. 중복인지는 유사도와 임계값을 비교해서 정하므로, 같은 기사·같은 설정이면 결과가 항상 같습니다. LLM은 다음 단계(관련/무관 판정)에서만 씁니다.
- **검색어 문단:** 수집한 본문에는 문단 구분(줄바꿈)이 없습니다. 크롤러가 줄바꿈을 공백으로 합치기 때문입니다. 그래서 **검색어·별칭이 든 문장 ± k문장**을 문단으로 봅니다.
  - k는 `DEDUP_PASSAGE_WINDOW`(기본 2, 처음엔 1)입니다. 검색어가 여러 문장에 나오면 구간을 합쳐 본문 순서대로 잇고, 최대 2000자까지 씁니다.
  - 검색어는 대소문자·띄어쓰기·특수문자를 무시하고 찾습니다 ("M.I.B" = "MIB").
  - 본문에 검색어가 없으면 예전처럼 앞 N문장(`DEDUP_LEAD_SENTENCES`, 기본 5)을 씁니다. 라벨셋 988건 기준으로 이런 기사는 100건이었습니다.
- **발행일 기준은 넣었다가 뺐습니다.** "발행일 차이 3일 이상이면 중복 아님"을 시험해 봤는데, 날짜 기준이 맞지 않는 경우가 있어서 지웠습니다.
- **코드 변경 (다른 사람 코드에 영향 있음)**
  - `embed_for_dedup(articles, terms)`, `find_duplicates(..., terms=)`, `dedup_topic(topic_id, terms)`가 검색어 목록을 받습니다. 넘기는 값은 `selected.match_terms`(검색어 + 별칭)입니다.
  - 안 넘기면 content와 jaccard가 본문 앞 N문장으로 비교합니다.
  - `Article.lead_embedding` 필드 이름이 `passage_embedding`으로 바뀌었습니다.

**중복 제거 확인 스크립트 (`experiments/check_dedup.py`)**
- `python experiments/check_dedup.py`로 실행합니다. 검색어 → 의미 번호 → 기간(Enter = 30일) → 최대 기사 수(Enter = 100건)를 차례로 묻습니다. `--target 강남 --sense "방송인 강남" --days 30 --max 100`처럼 인자로 줘도 됩니다.
- 하는 일: 검색·크롤링 → 지금 `.env` 기준으로 중복 제거 → **중복으로 걸린 기사**(대표 기사별로 묶음)와 **중복 안 걸린 기사**를 보여 줍니다.
- 결과는 터미널에 나오고, 링크와 본문 앞부분을 붙여 `experiments/results/check_dedup_검색어_의미_날짜시각.md`로도 저장합니다.
- DB에는 저장하지 않고 LLM 판정도 하지 않습니다. 의미 후보만 DB 캐시에서 읽습니다.

**확인 결과 (강남 → 방송인 강남, 서울여대 → 서울여자대학교)**
- **content(검색어 문단)는 대체로 맞게 묶었습니다.** 같은 사안끼리 0.7~0.83이 나왔습니다.
  - 약점: 검색어 문장이 "방송인 강남이 유튜브 채널 '동네친구 강나미'에서…"처럼 매번 비슷한 소개 문장이면, 회차가 다른 기사도 비슷하게 나옵니다.
- **잘못 묶이는 건 대부분 `noun` 하나 때문입니다.** 다시 크롤링해 확인했을 때 noun만 넘어서 묶인 쌍이 강남은 중복 40건 중 17건, 서울여대는 42건 중 18건이었습니다.
  - 제목의 고유명사가 **검색어 하나뿐**이면 noun 유사도가 1.0이 됩니다. 예: 이서진 예능 기사 ↔ 강남 재건축 기사, "서울여대 근육 재생 연구" ↔ "서울여대·동지사여대 AI 협력".
  - 'AI'만 있는 제목끼리도 같은 문제가 생깁니다.
  - 임계값 0.3이 낮아서 공통 단어 하나만 겹쳐도 넘어갑니다.
- 같은 사안인데 여러 묶음으로 쪼개진 경우도 있습니다. 예: 디올 CEO 이화여대 학위식 기사가 6개 묶음으로 나뉘었습니다.

### 1-2. 이전 변경 (2026-11-09)

**정답 라벨링 → JSON 평가셋 (`evalset/`)**
- `python evalset/build_labeled_set.py`: 한 번 실행하면 **검색어를 계속 받아** 라벨링하고, 검색어에 `q`를 넣으면 끝납니다.
  - 흐름: 검색어 → 기간(Enter = 30일) → LLM 의미 후보에서 고르기 → 수집 → 중복 제거(대표 기사만) → 최신 대표 기사부터 **1 관련 / 2 무관** (s 건너뛰기, q 이 검색어 그만)
  - 결과는 **`evalset/labeled_set_1.json`, `labeled_set_2.json`, …** 에 검색어 단위로 나눠 쌓입니다 (파일당 약 3.5MB, 한 검색어는 한 파일에만, `evalset/labeled_store.py`). 라벨마다 바로 저장하고, 다시 실행하면 그 검색어가 든 파일(새 검색어면 마지막 파일, 자리가 없으면 다음 번호)에 이어서 씁니다 (이미 붙인 기사는 다시 안 물어봄, 검색어 × 의미당 150건까지).
  - 항목 형식: `title`, `url`, `description`, `content`, `query`, `sense`(고른 의미 + 별칭·연관어·배제어·고르지 않은 의미), `label`(true/false)
  - `old/build_labeled_set.py`를 옮긴 것입니다. 라벨은 DB에 쓰지 않습니다.
- **실험 A를 `evalset/exp_a_filtering.py`로 옮기고 정답 JSON으로 평가**합니다 (`python evaluate.py exp-a`도 같은 실험, 자세히는 10장).

**검색 방식 (1단계)**
- **검색어 단독 검색을 뺐습니다.** "검색어 + 연관어"(연관어 전부, 최대 8개)와 별칭만 검색합니다. 연관어·별칭이 하나도 없을 때만 검색어 단독.
- 이유: "강남"을 그대로 섞어 검색하면 기사가 많은 지역 강남이 상한을 채워서 방송인 강남 기사가 라벨 목표(150건) 안에 잘 안 들어왔습니다 (예전: 방송인 강남 300건 중 100건이 "강남" 단독 결과 → 지금 0건). 서비스도 같은 방식입니다.

**`targets.yaml` 삭제 — 의미·연관어는 LLM 후보만**
- 사람이 적은 정의·별칭·연관어로 LLM 값을 덮어쓰던 기능을 없앴습니다. 모든 곳(서비스·관리·라벨링·실험)이 LLM 의미 후보(DB `query_senses`에 캐시)만 씁니다.
- 대상 목록은 **DB에 저장된 topic**입니다. 새 대상은 `python admin.py collect 강남`(의미 고르기 → 수집 → 중복 제거)으로 추가하고, `collect-all` / `filter-all` / `index-all`은 저장된 topic 전부를 처리합니다. 일괄 명령은 시작할 때 topic 기준을 LLM 후보 값으로 다시 맞춥니다.
- 실험 A의 1-b 검증어(예전 "검증 키워드" 재현용)는 `evalset/exp_a_filtering.py`의 `VALIDATION_TERMS`로 옮겼습니다.
- 남은 한계: LLM이 지어낸 별칭(예: 방송인 강남 → "전형수")도 그대로 쓰입니다.

**고친 버그**
- **LLM 형식 응답이 전부 실패하던 문제**: 지금 채팅 모델(`claude-fable-5-1`)은 게이트웨이에서 도구 호출 강제(`tool_choice`)를 지원하지 않아 400 에러가 났고, 코드가 에러를 삼켜 "의미 후보 없음"·"판정 못 함"이 됐습니다 (DB에 후보가 캐시된 강남·애플만 정상이었음). → `qupict/llm.py`의 `get_structured_model()`(`json_schema` 방식)로 통일 (의미 후보, 직접 입력 의미, LLM 판정, 질문 세트). **이전에 `filter-all`을 돌렸다면 판정 못 한 기사가 남아 있을 수 있으니 다시 실행하세요.**
- **임베딩 토큰 한도 초과**: 기사 279건을 한 요청에 보내 `Requested 351651 tokens, max 300000` 에러 → 한 요청에 100건씩 나눠 보냄 (`EMBED_BATCH_SIZE`).
- **Windows `WinError 10054` 로그**: 크롤링 중 언론사 서버가 연결을 끊으면 `Exception in callback _ProactorBasePipeTransport...`가 찍히던 문제 → `setup_console()`에서 Windows asyncio 루프를 Selector 방식으로 바꿈 (동작에는 영향 없던 로그).

| 실행 파일 | 누구를 위한 것 | 쓰는 데이터 |
| --- | --- | --- |
| `run.py` | **서비스** 사용자 (질문하고 답 받기, 터미널) | 서비스 DB |

| `evalset/build_labeled_set.py` | 정답 라벨링 (JSON) | 정답 JSON |

**서비스 (`run.py`)**

| 명령 | 하는 일 |
| --- | --- |
| `python run.py 애플 30` | 검색어 + 기간 → 의미 고르기 → 수집 → 필터 → 인덱싱 → **질문** (DB 버전). `--max 30`으로 수집 건수 제한 |
| `python run.py 애플 30 --memory` | DB 없이 메모리에서 (예전 방식, FAISS) |
| `python web.py` | 웹 화면으로 같은 흐름 (브라우저에서 `http://localhost:8000`). 많이 보도된 기사 Top 5, 준비 중 질문 적어 두기 (3번 과정이 모두 끝나면 답함, 위 최신) |
| `python web.py --port 8080` / `--host 0.0.0.0` | 포트 바꾸기 / 같은 네트워크의 다른 컴퓨터에서도 접속 (팀원 시연용) |

**서비스 DB 관리 (`admin.py`) · 평가 (`evaluate.py`)**

| 명령 | 하는 일 |
| --- | --- |
| `python admin.py collect 강남` | **새 대상 추가**: LLM 의미 후보에서 고르기 → topic 저장 → 수집 → 중복 제거 (0·1·2단계). 대상당 최대 **300건** (`--max`), 끝나면 대표 기사 수를 알려 줌 |
| `python admin.py collect-all` | DB에 저장된 대상(topic) 전부 다시 수집 → 중복 제거. 새 기사만 크롤링 |
| `python admin.py filter-all` | 전부 필터링 (2·3단계). `--redo`: 판정을 지우고 처음부터 (정답 라벨은 유지) |
| `python evaluate.py label` | **대상당 최신 대표 기사 150건에 정답 라벨** (1 관련 / 2 무관 / 3 보류 / s 건너뛰기 / b 이전 / q 끝). `--limit`로 목표 변경. 중복 제거는 임베딩만 써서 LLM 비용 없음, `filter-all` 전에 해도 됨 |
| `python admin.py index-all` | 전부 인덱싱 (4단계). `--no-images`: 이미지 설명 없이 (LLM 비용 0) |
| `python admin.py status` | topic별 현황: 기사·중복·판정·라벨·청크 수 |
| `python admin.py init-db` | DB 테이블 만들기 |

- **대상 = DB에 저장된 topic**입니다 (예전 `targets.yaml`은 지웠습니다). 새 대상은 `collect 검색어`로 추가하고, 일괄 명령(`*-all`)은 저장된 topic 전부를 처리합니다.
- **의미·별칭·연관어는 LLM이 만든 의미 후보만 씁니다** (사람이 적은 값으로 덮어쓰지 않음). 일괄 명령은 시작할 때 topic의 기준을 LLM 후보 값으로 다시 맞춥니다.
- 일괄 명령은 모두 `--target 강남`처럼 **검색어 하나만** 할 수 있습니다.
- 모든 명령은 **아직 안 한 것만** 처리합니다 → 중간에 끊겨도 다시 실행하면 이어서 하고, 비용이 다시 들지 않습니다.
- 답변의 출처에는 **답변이 실제로 인용한 기사만** 보여 줍니다 (`Answer.cited`).
- **라벨 기준: 대상당 중복 제거 후 최신 대표 기사 150건.** `label`은 이미 붙인 라벨 수를 빼고 최신 기사부터 남은 개수만 보여 주고, 150건을 채운 대상은 목록에서 빠집니다. 건너뛴(s) 기사는 다음 실행 때 다시 나오니, 판단이 어려운 기사는 3(보류)으로 표시하세요.
- 150건이 남도록 `collect-all`은 대상당 **최대 300건**을 모읍니다 (검색어마다 최신순 최대 300건까지 쪽을 넘겨 받음, 강남 30일 기준 후보 약 700건). 수집 결과에 "⚠ 라벨 목표 150건보다 N건 적음"이 나오면 안내대로 `--max` 또는 `--days`를 늘려 다시 실행하세요 (이미 있는 기사는 다시 크롤링하지 않음).
- `label`은 시작할 때 **중복 기사부터 표시**합니다 (2단계와 같은 기준, 1-1 참고). 비슷한 기사는 대표 기사 하나만 보여 주므로 같은 내용을 여러 번 라벨링하지 않습니다. LLM 판정은 하지 않아서 `filter-all` 없이 바로 라벨링할 수 있습니다.
- **라벨 붙인 기사는 중복으로 바뀌지 않습니다.** 나중에 기사를 더 수집하거나 `filter-all --redo`를 해도 라벨 붙은 기사는 대표로 남습니다 (중복이 되면 실험 A에서 빠지기 때문).
- `label`은 시스템 판정을 보여 주지 않습니다 (정답이 시스템 판정에 끌려가지 않게). 5건마다 모아서 저장하고, 끝낼 때(q)도 저장합니다.

```bash
python admin.py collect 강남      # 대상마다 한 번 (의미를 골라 추가). 같은 검색어의 다른 의미도 다시 실행해 추가
```
```bash

```
```bash
python admin.py status
```

0. **라벨링 (JSON)**: 사람마다 다른 검색어를 맡아 `build_labeled_set.py`로 라벨링 → 각자 만든 `labeled_set_N.json`을 합치거나 한 사람이 이어서 작업. `evaluate.py label`(DB에 라벨 저장)은 예전 방식이라 실험 A에는 쓰이지 않습니다
1. **collect**: 대상마다 의미를 골라 추가 → 최대 300건 수집 → 중복 제거. 이후 다시 모을 때는 `collect-all`. 네이버 검색은 무료, 처음 보는 검색어만 의미 후보 LLM 호출 (약 0.3 크레딧씩), 중복 제거는 임베딩만 (거의 0). 대상마다 "대표 기사 N건"이 150 이상인지 확인
2. **label**: 대상당 최신 대표 기사 150건을 사람이 나눠서 라벨링 (12개 × 150 = 1,800건) — topic마다 번호를 골라서 하므로 **사람마다 다른 topic**을 맡으면 됩니다. 중복 제거는 LLM 비용이 없고, 시스템 판정 없이 라벨을 붙이므로 정답이 시스템에 끌려가지 않습니다
3. **filter-all**: 중복이 아닌 대표 기사 전부를 규칙·LLM으로 판정 (100건당 약 10~15 크레딧 → 대상당 대표 기사 약 200~250건이면 12개 합쳐 약 250~450 크레딧 예상). 라벨과 판정은 따로 저장되므로 label과 순서를 바꿔도 됩니다
4. **status**로 남은 라벨 수 확인
5. (나중에) **index-all**: 질문 답변·실험 B용. 이미지 설명 때문에 크레딧이 가장 많이 드는 단계라 따로 실행
6. **make-qa**: 라벨을 붙이며 기사를 읽은 김에 실험 B용 질문을 만든다 (`--suggest`면 LLM 초안). 대상마다 5~10개 정도

## 5. 0단계: 검색어 의미 선택 (`qupict/sense.py`)

### 동작

```text
검색어 "애플"
  → DB(query_senses)에 후보가 있으면 그대로 사용 (LLM 호출 없음)
    없으면 LLM이 의미 후보 생성 (자주 쓰이는 순, 최대 3개) → DB에 저장
      1. 기업 Apple   별칭 [Apple Inc.]  연관어 [아이폰, 맥북, 팀 쿡, iOS …]
      2. 과일 사과     연관어 [과수원, 농가, 수확, 사과값 …]
  → 하나 선택 (번호 / "기타" 직접 입력)
  → 결과(SelectedSense)
      기사에서 찾을 표기 = 검색어 + 별칭          → 1단계 수집
      배제어 = 고르지 않은 의미의 연관어          → 2단계 규칙 필터
      고르지 않은 의미 목록                       → 3단계 LLM 검증의 대조 기준
```

### DB 캐싱 (`load_sense_candidates`)

같은 검색어는 **처음 만든 후보만** 씁니다. LLM은 temperature=0이어도 실행마다 연관어가 조금씩 달라서, 캐싱이 없으면 배제어(2단계 기준)가 계속 바뀌어 실험을 재현할 수 없습니다.

| 상황 | 동작 |
| --- | --- |
| DB에 후보 있음 | DB 것 사용 (LLM 비용 0) |
| DB에 없음 | LLM으로 만들고 DB에 저장 |
| LLM이 후보를 못 만듦 (예: 베라) | 저장하지 않음 → 다음에 다시 시도 |
| `FIRESTORE_PROJECT` 없음 / DB 연결 실패 | 멈추지 않고 LLM만 사용 (경고 출력) |

- 실제 확인 (팀 공용 DB, "애플" 3번): 1회차 LLM → DB 저장, 2·3회차 DB에서 읽음. LLM 호출 1번, 세 번 모두 같은 결과
- `run.py`, `admin.py`, `python -m qupict.sense`, 라벨링 스크립트 모두 이 함수를 씁니다. DB 없이 LLM만 부르려면 `generate_sense_candidates`
- 후보를 **다시 만들고 싶을 때**: 지금은 DB의 해당 검색어 행을 지워야 합니다 (같은 이름은 덮어쓰지만, 이름이 바뀐 옛 후보는 남아서 섞이기 때문)

### 후보가 쌓이는 방식: 직접 입력 저장 + 많이 고른 순 (2026-11-15)

저장 위치는 **DB(`query_senses`)** 입니다. JSON · MD 파일 대신 DB를 쓴 이유:
웹 서버에 여러 사람이 동시에 들어와도 한 곳에 쌓이고(파일은 동시에 쓰면 깨지거나 덮어씀), 팀원 모두 같은 후보를 보며,
`topics.sense_id`가 이미 이 테이블을 가리키고 있어 의미 ↔ 수집 데이터가 이어져 있기 때문입니다.

| 상황 | 동작 |
| --- | --- |
| "기타"로 **새 설명** 입력 | LLM이 정리한 의미를 `is_custom = TRUE`로 저장 → **다음부터 이 검색어의 후보로 나옴** |
| 같은 설명을 다시 입력 / 저장된 직접 입력 후보 선택 | LLM을 부르지 않고 저장된 의미 사용 |
| 의미를 고를 때마다 | `use_count + 1`, `last_used_at` 기록 (`sense.remember_selection` → `db.record_sense_use`) |
| 후보 순서 | 많이 고른 순 → LLM 순위 → 직접 입력. 직접 입력 후보는 많이 고른 것 3개까지 (`MAX_SAVED_CUSTOM`) |
| 직접 입력만 저장된 검색어 (예전에 LLM이 후보를 못 만듦) | LLM을 다시 시도하고, 저장된 직접 입력을 뒤에 붙임 |

- **배제어는 그대로**: '다른 의미'(배제어 · LLM 대조 기준)는 지금처럼 LLM 후보만 씁니다. 직접 입력 후보는 LLM 후보와 겹치거나 더 넓은 대상일 때가 많아(예: "서울 소재 여자대학교" ⊃ 서울여자대학교), 배제어로 쓰면 원하는 기사를 걸러 버리기 때문입니다.
- 직접 입력 의미를 저장할 때 **포함 후보(`includes`)** 도 저장합니다 → 다음에 그 후보를 고를 때도 같은 '다른 의미'가 나옵니다.
- 웹 화면은 후보 옆에 "직접 입력 · N회 선택"을 표시하고, 순서가 바뀌어도 맞는 의미를 고르도록 번호 대신 **이름**(`sense_name`)으로 보냅니다.
- **이미 만든 DB는 `python admin.py init-db`를 한 번 실행**해야 새 열(`includes`, `use_count`, `last_used_at`)이 생깁니다. 예전 직접 입력 의미의 포함 후보 · 횟수는 저장된 topic에서 채웁니다. 실행 전에는 DB 읽기가 실패해 LLM으로 대신합니다 (멈추지는 않음).

### 발견한 LLM 문제와 대응

| 문제 | 예시 | 대응 |
| --- | --- | --- |
| 정보를 지어냄 | 방송인 강남 → 별칭 "조남식"·"전형수", 정의 "본명 조성민", 연관어 "비와이" | (예전: `targets.yaml`로 사람 값 덮어쓰기 → **지금은 지움**, LLM 값을 그대로 씀. 남은 한계) |

| 한자·외국 문자 | "出荷", "積雪" | **한자가 섞인 단어는 제거** (iOS, HBM 같은 영문은 유지) |
| 검색어 일부가 연관어로 | 서울여대 → "여대" (성신여대 기사까지 점수를 받게 됨) | **검색어 안에 포함된 단어는 연관어에서 제거** |
| 두 의미에 같은 단어 | 기업 Apple·과일 사과 둘 다 "가격" | 양쪽 모두에서 제거 (원래 있던 규칙) |
| 직접 입력이 LLM 후보와 같은 의미 | 직접 입력 "보건용 마스크" ↔ LLM 후보 "얼굴 마스크" → '방역', '황사'가 배제어가 됨 | **연관어가 2개 이상 겹치는 후보는 같은 의미로 보고 배제어에서 제외** |
| 너무 넓은 별칭 | 삼전 → '삼성' (삼성 라이온즈 기사까지 들어옴) | (예전: `targets.yaml`로 별칭 고정 → **지금은 지움**. 남은 한계) |
| 같은 입력에도 결과가 조금씩 다름 | temperature=0인데도 연관어가 실행마다 다름 | **DB에 첫 결과를 저장해 재사용** (`load_sense_candidates`) ✅ |

**남은 한계**: 배제어에 "인물", "출연" 같은 일반 단어가 섞일 수 있습니다 (예: 베라). 2단계 규칙 필터는 단어 하나로 바로 떨어뜨리지 않고 점수로 판단하고 3단계 LLM 검증도 있지만, 9개 대상은 사람이 결과를 한 번씩 확인하는 게 좋습니다.

## 6. 1단계: 뉴스 수집 (`qupict/collect.py`)

### 검색어 만들기

고른 의미로 네이버 검색어를 여러 개 만들어 **동시에** 검색합니다 (네이버 API는 무료).

| 순서 | 검색어 | 예: 눈 → 신체 기관 눈 | 이유 |
| --- | --- | --- | --- |
| 1 | 검색어 + 연관어 (전부, 최대 8개) | 눈 시력, 눈 안과, 눈 각막, ... | 고른 의미로 좁힌 검색 |
| 2 | 별칭 | 안구 | 같은 대상의 다른 이름 |

**검색어 단독("눈", "강남")은 검색하지 않습니다.** 섞어서 검색하면 기사가 많은 다른 의미(날씨 눈, 지역 강남)가 상한을 채워서, 고른 의미의 기사가 라벨 목표(150건) 안에 잘 들어오지 않았습니다 (예: 강남 → 방송인 강남 300건 중 100건이 "강남" 단독 결과). 고른 의미에 연관어·별칭이 하나도 없을 때만 검색어 단독으로 검색합니다.

검색어마다 최신순으로 최대 300건(100건씩 3쪽, 기간 밖으로 나가면 일찍 멈춤)을 받은 뒤 **검색어별로 돌아가며 하나씩** 뽑아 상한(`ask` 100건, `collect-all` 300건)을 채웁니다. 첫 검색어 결과만으로 상한이 차는 것을 막습니다.

### 기사마다 가져오는 것

| 항목 | 방법 |
| --- | --- |
| 본문 | 네이버 뉴스 주소가 있으면 거기서 먼저 (구조가 일정함), 실패하면 언론사 원문 |
| 언론사 | 네이버 로고 → 네이버 형식 "언론사 \| 네이버" → 언론사 사이트 이름 (기자 이름은 쓰지 않음) |
| 이미지 | 본문 속 사진 주소 + 원래 사진 설명(캡션), 기사당 최대 5장. 아이콘·로고·기자 프로필 사진은 제외 |
| 이미지 파일 | **DB에 저장하지 않음** (팀 결정). 4단계에서 관련 기사의 이미지 설명을 만들 때만 `download_images()`로 받아서 씀 (5KB 미만·5MB 초과는 버림) |
| 찾은 검색어 | 어떤 검색어로 들어온 기사인지 (분석·실험용) |
| 수집 시각 | 검색 결과가 날짜마다 달라지므로 기록 |

### 이미지 파일 내려받기

- **팀 결정: 이미지 파일은 DB에 저장하지 않습니다.** DB 용량을 아끼기 위해서입니다 (예전 Supabase 무료 500MB). DB(기사 문서의 `images`)에는 주소·캡션·LLM 설명만 저장합니다.
- 1단계(수집)는 주소·캡션만 저장하고, 파일은 **4단계에서 "관련" 기사의 이미지 설명을 만들 때만** `download_images()`로 받아 LLM에 보내고 버립니다.
- 받은 파일은 `ArticleImage.data`(바이트)와 `content_type`에 들어 있습니다 (메모리에서만 사용).
- 실제로 받아 보니 5KB 미만 파일은 기자 프로필 사진, 작은 그래픽, 미리보기 자리 이미지였습니다 → 버리도록 함.
- 확인 (기사 20건씩): 강남 39개 중 31개, 눈 34개 중 33개 받음 / 한 장 5~73KB, 대상 하나당 합계 약 0.7MB

### DB에 저장하기 (`collect_to_db`)

```python
result = await collect_to_db(selected, period_days=30)
print(result.summary())   # 검색 30건 → DB 재사용 12건 + 새로 저장 17건 (본문 실패 1건, 이미지 40개)
```

1. 고른 의미를 `topics`에 저장 (같은 검색어·의미면 기존 topic 재사용)
2. 네이버 검색 (무료라 매번 다시 함)
3. **DB에 이미 있는 기사는 크롤링하지 않고** `article_topics`로 연결만 함
4. 새 기사만 크롤링 → `articles`(이미지 포함), `article_topics`에 저장
5. 돌려주는 `CollectResult`: topic id, 검색·재사용·새로 저장·본문 실패 건수, 이미지 수

이후 단계는 `db.get_topic_articles(topic_id, period_days=...)`로 기사를 꺼내 씁니다.

### 실제 확인 (기사 30건씩)

| 대상 | 검색 → 본문 확보 | 언론사 확인 | 이미지 있는 기사 |
| --- | --- | --- | --- |
| 강남 / 방송인 강남 | 30 → 27 | 25 | 13 |
| 눈 / 신체 기관 눈 | 30 → 30 | 27 | 12 |

- **고친 기존 버그:** EUC-KR로 된 언론사 페이지를 UTF-8로 읽어 **본문 글자가 깨진 채** 저장되던 문제 → 페이지 문자셋을 판별해서 읽도록 수정 (깨진 본문 0건 확인)
- **남은 한계:** 일부 언론사는 본문 앞에 "홈 > 방송/TV" 같은 메뉴 글자가 섞입니다. 필요하면 언론사별 본문 위치를 추가하면 됩니다.
- "검색어 + 연관어"로 좁혀도 다른 의미 기사가 섞여 들어옵니다 (예: "강남 방송"에 지역 강남 기사). **이걸 걸러 내는 게 2·3단계의 역할**이고, 실험 A의 Baseline(API 결과 그대로)이 됩니다.

## 7. 2·3단계: 필터링 (`qupict/filtering.py`)

### 흐름

| 순서 | 단계 | 하는 일 | DB 저장 |
| --- | --- | --- | --- |
| 1 | 중복 제거 | 제목·검색어 문단·제목 고유명사·자카드 중 2개 이상이 임계값을 넘으면 같은 사안 (1-1 참고) → 본문이 가장 긴 기사만 대표로 | `article_topics.duplicate_of` |
| 2 | 1차 규칙 (`stage=rule`) | **분명히 아닌 것만** 무관 처리 (아래 표) | `status='무관'`, `reason` |
| 3 | 2차 LLM (`stage=llm`) | 고른 의미 vs 고르지 않은 의미를 대조해 **관련 / 무관 / 보류 + 근거 한 줄** | `status`, `reason`, `judged_model` |

**규칙 점수** (기획안 방법 1-c) = 연관어 점수 − 배제어 점수, 단어마다 제목에 있으면 2점·본문에만 있으면 1점

| 경우 | 판정 |
| --- | --- |
| 검색어·별칭이 기사에 아예 없음 (예: "서울여대" 검색에 걸린 성신여대 기사) | 무관 (rule) |
| 점수 ≤ −2 (다른 의미 단어가 분명히 더 많음) | 무관 (rule) |
| 나머지 | LLM으로 |

- 규칙으로 "관련"은 주지 않습니다. 단어만으로는 실제 주제와 단순 언급을 구분할 수 없어서입니다.
- 기준값(−2)은 정답 라벨이 생기면 실험으로 조정합니다 (`filtering.RULE_REJECT_SCORE`).
- 질문 답변(run.py)에는 **관련 + 보류** 기사를 씁니다. 확신 없는 기사를 버리면 놓치는 정보가 생기기 때문입니다.

### 사용

```python
outcome = await filter_articles(articles, selected)        # 메모리 버전 (run.py)
outcome = await filter_topic(topic_id, selected)           # DB 버전: 새 기사만 판정해서 저장
outcome = await filter_topic(topic_id, selected, redo=True) # 규칙·프롬프트를 바꿨을 때 전부 다시 (정답 라벨은 유지)
print(outcome.summary())   # 중복 0건 | 규칙 무관 0건 | LLM 관련 6 · 무관 3 · 보류 0건
```

- DB 버전은 **아직 판정 안 한 기사만** 처리하고, 이미 판정한 기사와 비슷한 새 기사는 중복으로 표시합니다. 기사 임베딩도 DB에 저장해 다시 계산하지 않습니다.
- LLM이 답하지 못한 기사는 판정하지 않고 남겨서 다음 실행 때 다시 시도합니다.

### 실제 확인 (팀 공용 DB, 방송인 강남 9건)

| 판정 | 기사 | 근거 (LLM) |
| --- | --- | --- |
| 관련 6 | 괌 관광객 구조, 이서진 밥값 내기, 드라마 OST 등 | "가수 강남이 … 구한 내용이 주 소재" 등 |
| 무관 3 | 로또 판매점 목록 | "'서울 강남구 삼성로' 등 지역명 언급" |
| | 박서진 성형 시술 | "'강남'은 피부과 시술을 다녀온 '지역 강남'을 뜻함" |
| | 김수찬 공연 | "'성남과 인천, 강남 등' 지역 공연 일정 나열" |

- **고친 점:** 처음엔 LLM이 판정을 먼저 쓰고 근거를 나중에 써서, 근거는 "지역 의미, 무관 쪽"인데 판정은 '관련'인 경우가 있었습니다. **근거를 먼저 쓰고 판정하게** 답 형식 순서를 바꿔서 해결했습니다.
- 비용: 9건 판정 약 1~2 크레딧, 13초

## 8. 4·5단계: 인덱싱·검색·답변 (`indexing.py`, `retrieval.py`, `qa.py`)

### 4단계 인덱싱 (`index_topic`)

| 순서 | 하는 일 | 저장 |
| --- | --- | --- |
| 1 | **이미지 설명**: 관련·보류 기사의 이미지를 LLM이 2~3문장으로 설명 (기사당 최대 2장) | `articles`의 `images.{이미지}.llm_description` |
| 2 | **청크**: 본문을 약 500자씩 문장 단위로 자름 (앞 청크의 마지막 문장을 겹쳐서 시작). 이미지 설명은 1장 = 청크 1개 | |
| 3 | **임베딩**: 청크마다 (기사 제목 + 청크)로 임베딩 | `chunks` (source = body / image) |

- 청크가 없는 기사 + 이번에 이미지 설명이 새로 생긴 기사만 처리 → 여러 번 실행해도 안전
- `describe_images=False`: 이미지 설명 없이 (LLM 비용 0) / `rebuild=True`: 청크 규칙을 바꿨을 때 전부 다시
- **이미지는 주소를 LLM에 그대로 넘기고, 실패하면 파일을 받아서 보냅니다.** 실제로 해 보니 게이트웨이가 WebP·일부 JPEG 파일을 직접 올리면 거절했지만 주소로는 됐습니다.
- **비용 주의**: 이미지 1장 설명 ≈ 의미 후보 1번과 비슷 (입력 약 470토큰). 12개 대상 × 관련 기사 50건 × 2장이면 수백 크레딧이 될 수 있어 기사당 2장으로 제한

### 5단계 검색 (`search_topic`) + 답변 (`generate_answer_from_chunks`)

```text
질문 → [원 질문 + HyDE 가상 문장, Multi-Query 변형 질문 2개]
     → 각 문장으로 DB 벡터 검색: 조건(topic · 관련/보류 · 최근 N일) 안에서 청크 유사도 (예전 pgvector, 지금 Firestore)
     → 같은 청크는 가장 높은 유사도로 합침, 0.5 미만 버림 → 상위 5개
     → 기사별로 묶어 (기사 N) 번호 → LLM 답변 + 출처 (근거 종류: 본문 / 이미지 설명)
```

- 기사 전체 대신 **청크만** 넣어서 답변 LLM에 들어가는 글이 크게 줄었습니다 (예전 기사 10건 × 6,000자 → 청크 5개 × 약 500자)
- 이미지 설명을 근거로 쓰면 답변에 "(기사 N, 이미지)", 출처에 `[이미지 설명]`으로 표시 (기획안 요구사항)
- FAISS 메모리 버전(`build_in_memory_store`, `retrieve_relevant_articles`)은 실험 B 비교용으로 남겨 둠

### 실제 확인 (팀 공용 DB, 방송인 강남 관련 6건)

| 단계 | 결과 |
| --- | --- |
| 인덱싱 | 본문 청크 22개 + 이미지 청크 9개 |
| "강남이 괌에서 무슨 일을 했어?" | 괌 동굴에서 관광객 구조 — 두 기사 인용, 정답 |
| "밥값 내기에서 얼마를 냈어?" | 1,519싱가포르달러(150만 원대) — 정답 |
| "괌 영상 사진에는 어떤 모습이?" | 이미지 청크 5개 검색 → "(기사 1, 이미지)" 인용, 출처 `[이미지 설명]` |

- 질문 1개당 약 8~14초 (HyDE·Multi-Query LLM 2번 + DB 검색 3번 + 답변). 당시 DB(Supabase)가 싱가포르 리전이라 DB 검색이 느린 편이었음 → 지금은 서울 Firestore (위 DB 이전)

## 9. DB (`qupict/db.py`, Google Cloud Firestore)

2026-11-16에 Supabase(PostgreSQL + pgvector)에서 Firestore로 옮겼습니다 (위 "DB 이전"). 아래 규칙은 그대로입니다.

### 9-1. 컬렉션 (예전 테이블 → Firestore)

| 컬렉션 / 문서 id | 내용 | 단계 |
| --- | --- | --- |
| `query_senses/{hash(검색어, 이름)}` | 검색어별 의미 후보: LLM 후보 + "기타"로 직접 입력해 저장된 의미, 고른 횟수 | 0 |
| `topics/{정수 id}` · `topic_keys` · `counters/topics` | 검색어 + 고른 의미, 배제어, 대조할 다른 의미, 마지막 수집 시각. 번호는 `counters/topics`에서 트랜잭션으로 발급 | 0 |
| `articles/{link 해시}` | 제목, 링크, 발행일, 언론사, 본문, 수집 시각, 기사 임베딩, 청크 수 + **`images` 맵**(이미지 주소 · 캡션 · LLM 설명/OCR 글자) — 예전 `article_images` | 1·4 |
| `article_topics/{topic id}_{기사 키}` | topic별 기사 판정: 찾은 검색어, 중복 표시(대표 기사 키), 판정 · 단계 · 근거, 정답 라벨. 조인 대신 link · 발행일 · 청크 유무를 복사해 둠 | 2·3 |
| `chunks/{기사 키}_{번호}` | 청크 텍스트(본문/이미지) + 임베딩 + `search_keys`("topic id:판정", 대표 기사로 판정된 topic만) + 출처 표시용 제목 · 언론사 · 발행일 | 4·5 |

**검색 인덱스** (`python admin.py init-db`가 만듦, 처음 한 번): `article_topics`(topic_id + pub_date), `chunks` 벡터 인덱스 2개(search_keys [+ pub_date] + embedding 1536차원). 나머지 조건은 Firestore가 자동으로 만드는 인덱스로 됩니다.

### 9-2. 정한 규칙

| 규칙 | 내용 | 이유 |
| --- | --- | --- |
| 기사는 한 번만 저장 | 기사 문서 id = link 해시. 여러 topic에 걸린 기사는 `article_topics`로 연결 | 본문·이미지 설명·청크·임베딩을 한 번만 만듦 (크레딧 절약) |
| 기간 = 발행일 | topic에는 기간을 저장하지 않음. 조회할 때 **[질문한 시각 − N일, 질문한 시각]** 안에 발행된 기사만 | 같은 topic을 기간만 바꿔 다시 쓸 수 있음. 과거 시점 기준 재현도 가능 (`now=` 인자) |
| 같은 topic 재사용 | (검색어, 의미 이름)이 같으면 같은 topic. 다시 요청하면 검색은 다시 하되, **DB에 있는 기사는 크롤링 안 하고 새 기사만** 가져와 저장 | 수집은 한 번만, 최신 기사만 추가 |
| 중복 표시 | `duplicate_of`(대표 기사)에 값이 있으면 중복. 중복 기사는 따로 판정하지 않고 **대표 기사의 판정을 복사**해 받음 (`db.copy_duplicate_judgments`) | 판정이 빈 행이 없게. 검색·청크에는 대표 기사만 씀 |
| 판정 ≠ 정답 | `status`(시스템 판정, `stage` = rule/llm)와 `label`(사람이 붙인 정답)은 별도 필드 | 실험에서 둘을 비교 |
| 판정과 검색 대상 | 판정 · 중복 표시를 바꾸는 함수는 그 기사 청크의 `search_keys`도 같이 바꿈 (`db._sync_search_keys`) | 조인 없이 topic · 판정으로 검색을 거르기 위해 |
| 필터 다시 돌리기 | `reset_topic_filter`로 판정만 지우고 다시 실행 (정답 라벨은 유지) | 규칙 수정 → 해당 단계만 재실행 |
| 임베딩 1536차원 | `text-embedding-3-small`. 모델을 바꾸면 `db.EMBEDDING_DIM`과 벡터 인덱스(`init-db`)도 바꿔야 함 (Firestore 최대 2048) | |

### 9-3. 팀 공용 DB (Firestore)

DB는 팀 공용 하나(GCP 프로젝트 `qupict`의 Firestore `(default)`, 서울)를 씁니다. 한 명이 수집한 기사·판정·라벨을 모두가 같이 봅니다. 연결 방법은 위 3-4.

| 항목 | 내용 |
| --- | --- |
| 권한 | 프로젝트 주인이 팀원에게 `Cloud Datastore 사용자` 역할을 줍니다 (IAM). 키 파일은 쓰지 않습니다 (조직 정책으로 막혀 있음) |
| 비용 | 무료 한도: 하루 읽기 5만 · 쓰기 2만 · 삭제 2만, 저장 1GiB. 넘으면 결제 계정에 과금. `admin.py collect-all` · 실험처럼 많이 읽는 일은 몰아서 돌리지 않기 |
| 같이 쓰는 DB | `reset_topic_filter`, 문서 삭제 같은 지우는 작업은 **팀에 먼저 말하기** |
| 구조 변경 | 테이블 정의가 없어서 새 필드는 저장할 때 생깁니다. 이미 있는 문서에 값을 채워야 하면 `tools/`에 일회성 스크립트를 만들어 돌립니다 |
| 비용·크레딧 | 같은 topic을 두 사람이 동시에 수집하지 않기 (LLM 크레딧이 두 번 듦) |
| 데이터 보기 | GCP 콘솔 → Firestore → Firestore Studio |
| 예전 Supabase | 이전 확인용으로 남겨 둠 (읽기만). 사이트가 새 코드로 바뀌기 전 Supabase에 새로 쌓인 데이터는 `python tools/migrate_supabase_to_firestore.py --force`로 다시 맞춥니다 |

### 9-4. 단계별로 쓰는 함수 (각 단계 담당)

기사는 id 대신 **link**로 가리킵니다. 지금의 `Article` 객체를 그대로 넘기면 됩니다.

| 단계 | 함수 | 하는 일 |
| --- | --- | --- |
| 공통 | `init_db()` | 검색 인덱스 만들기 (`python admin.py init-db`) |
| 0 | `get_sense_candidates(query)` / `save_sense_candidates(c)` / `record_sense_use(query, sense, includes)` | 의미 후보 캐시 읽기 / 저장 / 고른 의미 기록 (횟수 +1, 새 직접 입력 저장) |
| 0 | `save_topic(selected)` → topic id, `get_topic(query, sense_name)` | topic 만들기·재사용 / 읽기 |
| 1 | `collect.collect_to_db(selected, period_days)` → topic id | **1단계 DB 버전 (완성)**: topic 저장 → 검색 → 이미 있는 기사는 연결만 → 새 기사만 크롤링·저장 |
| 1 | `link_known_articles(topic_id, metas)`, `save_articles(topic_id, articles)` | 위 함수가 안에서 씀 |
| 2·3 | `get_topic_articles(topic_id, period_days=, statuses=, include_duplicates=, unjudged_only=)` | 조건에 맞는 기사 (임베딩·이미지 포함) |
| 2·3 | `save_article_embeddings(articles)` | 기사 임베딩 저장 (다음에 다시 계산 안 함) |
| 2·3 | `save_duplicates(topic_id, {중복 link: 대표 link})` | 중복 표시 |
| 2·3 | `save_judgments(topic_id, [Judgment(link, status, stage, reason, model)])` | 관련/무관/보류 판정 |
| 2·3 | `save_labels(topic_id, {link: 라벨})`, `reset_topic_filter(topic_id)` | 정답 라벨 / 판정 초기화 |
| 4 | `get_images_to_describe(topic_id)`, `save_image_description(image_id, text)` | 설명 없는 이미지 / 설명 저장 |
| 4 | `get_articles_without_chunks(topic_id)`, `save_chunks(link, [Chunk(...)])` | 청크 없는 기사 / 청크 교체 저장 |
| 5 | `search_chunks(topic_id, 질문 임베딩, k, period_days=)` | topic·판정·기간 조건 + 벡터 유사도 top-k (출처 기사 포함) |

> **필터링 담당 참고:** 같은 topic에 새 기사가 들어오면 `unjudged_only=True`로 새 기사만 꺼내고, 중복 비교는 이미 있는 대표 기사(`include_duplicates=False`)와도 해야 합니다. 기사 임베딩은 DB에 있으니 다시 계산하지 않아도 됩니다.

- 모두 `--target 강남`처럼 검색어 하나만 할 수 있고, 결과는 `experiments/results/`에 `실험_날짜시각.json/.csv`로 저장됩니다 (CSV는 엑셀에서 바로 열림).

- **실험 A는 `evalset/`으로 옮겼고 정답 JSON으로 평가합니다.** 기준(의미·연관어·배제어)은 라벨링 때 JSON에 저장한 값을 쓰고, 규칙·LLM 판정을 그 자리에서 다시 계산합니다. LLM 판정은 `evalset/results/llm_cache.json`에 캐시 (다시 돌려도 비용 0), 결과는 `evalset/results/`.

- **질문 세트**: `experiments/qa_set.csv` 하나만 봅니다 (git에 올려 팀이 같이 씀, 엑셀로 편집 가능). 아래 "질문 세트(골든셋) CSV" 참고.

### 강남으로 시험 실행한 결과 (질문 3개, 참고용)

| 실험 | 결과 |

### 유사도 기준 0.5 (팀 결정)

- `RELEVANCE_SIMILARITY_THRESHOLD` (기본 0.5, `.env`로 바꿀 수 있음): 질문과 청크의 유사도가 이 값 미만이면 답변 근거로 쓰지 않습니다.
