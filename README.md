## 왜 만들었나

| 기존 뉴스 검색의 불편 | QuPicT의 해결                                          |
| --- |-----------------------------------------------------|
| '서울여대', '눈'처럼 뜻이 여러 개인 검색어는 다른 의미의 기사가 섞여 나옴 | **검색어 의미 구분** — 의미를 고르면 그 의미의 기사만 남김                |
| 핵심 수치가 사진 · 표 · 인포그래픽 안에만 있으면 찾을 수 없음 | **본문 + 사진 통합 분석** — 사진 속 글자(OCR)까지 답변에 반영           |
| 같은 사건을 여러 언론사가 비슷하게 보도해 같은 내용을 반복해서 읽음 | 중복 기사를 묶어서 **주요 이슈 브리핑** — 많이 보도된 이슈 Top 5를 먼저 보여 줌 |
| LLM 답변은 최신 소식이 빠지거나 근거를 알기 어려움 | **근거 기반 질의응답** — 최신 기사로 답하고 제목 · 원문 링크 제시           |

**활용 대상**: 최신 이슈를 빠르게 파악하려는 일반 사용자 · 특정 기업/인물/주제를 추적하는 사용자 · 뉴스 자료를 조사하는 대학생과 연구자

## 주요 성과

| 항목 | 기존 | **QuPicT** | 변화 |
| --- | ---: | ---: | ---: |
| 기사 필터링 정밀도 (Precision) | 0.41 | **0.59** | +17.3%p |
| 기사 필터링 F1 | 0.58 | **0.72** | +13.4%p |
| 검색 Recall@5 (정답이 상위 5개 안에 든 비율) | 29.9% | **62.1%** | +32.2%p |
| 검색 MRR (정답이 얼마나 앞 순위인지) | 0.279 | **0.502** | +0.223 |

- 필터링 재현율은 1.00 → 0.93으로 조금 낮아졌지만, 답변 정확도에 직접 영향을 주는 **정밀도를 우선**했습니다.
- 검색 정확도를 높이면서 **검색 시간은 그대로**(질문당 약 0.9초)입니다.

## 동작 방식

```text
 검색어 "강남"
   ▼
 ① 의미 구분      LLM이 의미 후보 제시 → 사용자 선택       1. 방송인 강남  2. 지역 강남  / 직접 입력
   ▼
 ② 뉴스 수집      의미별 검색어로 네이버 뉴스 수집 → 본문 · 사진 · 캡션 크롤링
   ▼
 ③ 필터링         중복 묶기 → 규칙 필터 → LLM 판정 (관련 / 무관)
   ▼
 ④ 멀티모달 처리  본문 분할 + 사진 속 글자(OCR) → 임베딩 → Firestore 벡터 DB
   ├──▶ ⑤ 이슈 브리핑   가장 많이 묶인 이슈 Top 5
   ▼
 ⑥ 질의응답       하이브리드 검색(벡터 + BM25) → 근거 인용 답변 + 출처 링크
```

| 단계 | 핵심 내용                                                                                                                | 사용 기술 |
| --- |----------------------------------------------------------------------------------------------------------------------| --- |
| ① 의미 구분 | 의미 후보 1~3개 + 정의 · 별칭 · 연관어 생성. **고르지 않은 의미의 연관어는 배제어**로 사용. 후보는 DB에 저장해 같은 검색어엔 같은 결과가 나오며 많이 활용된 순으로 최대 3개의 의미를 제공. | LLM, Firestore |
| ② 뉴스 수집 | 별칭 · 연관어로 검색어 여러 개를 만들어 동시 검색. 기사 64건 동시 다운로드, 본문 해석은 여러 프로세스로 병렬 처리. **이미 저장된 기사는 재사용**                             | 네이버 뉴스 API, BeautifulSoup, asyncio |
| ③ 필터링 | 비슷한 기사는 대표 하나로 묶음 → 규칙 점수로 분명한 무관 제거 → LLM이 8건씩 묶어 판정. 중복 기사는 대표 기사 판정을 그대로 사용                                       | 임베딩 · 형태소 분석, LLM |
| ④ 멀티모달 처리 | 본문 청크 + 사진 속 글자를 1536차원 벡터로 저장                                                                                       | EasyOCR, text-embedding-3-small, Firestore 벡터 검색 |
| ⑤ 이슈 브리핑 | 묶인 기사가 많은 이슈 5건을 **기사 속 문장 그대로** 요약 (LLM 없음, 왜곡 없음)                                                                  | Kiwi 형태소 분석 |
| ⑥ 질의응답 | 벡터 검색(의미) + BM25(인물명 · 기업명 등 핵심 단어)를 **RRF로 합침** → 답변에 제목 · 원문 링크                                                    | Hybrid Search, `gemini-3.5-flash-lite` |

**고른 의미에 따라 연관어와 배제어가 뒤바뀝니다. 다음 표는 예시입니다.**

| 검색어 | 고른 의미 | 연관어 (찾을 단어) | 배제어 (걸러낼 단어) |
| --- | --- | --- | --- |
| 당근 | 당근마켓 | 중고거래, 동네생활, 당근페이 | 농가, 수확, 당근즙 |
| 당근 | 채소 당근 | 농가, 수확, 당근즙 | 중고거래, 동네생활, 당근페이 |
| 애플 | 기업 Apple | 아이폰, 맥북, iOS | 과수원, 사과값, 품종 |
| 애플 | 과일 사과 | 과수원, 사과값, 품종 | 아이폰, 맥북, iOS |

## 성능 평가

### 실험 A — 관련성 필터링

9개 topic(검색어 × 의미), **직접 정답 라벨을 붙인 기사 988건** 기준 · `python evaluate.py exp-a`

| 방법 | Precision | Recall | F1 | LLM 호출 |
| --- | ---: | ---: | ---: | ---: |
| baseline (API 결과 그대로) | 0.412 | 1.000 | 0.584 | 0 |
| 별칭 포함 여부 | 0.439 | 0.963 | 0.604 | 0 |
| 규칙 점수만 | 0.482 | 0.774 | 0.594 | 0 |
| LLM 판정만 | 0.578 | 0.953 | **0.720** | 126 |
| **제안 (규칙 → LLM)** | **0.585** | 0.929 | 0.718 | **115** |

- 제안 방식은 LLM만 쓸 때와 성능이 비슷하면서 **LLM 호출이 더 적습니다** (126 → 115).
- 동음이의어가 뚜렷한 '방송인 강남'은 Precision 0.105 → **1.000**.

### 실험 B — 검색 방식

골든셋 87문항 · **정제된 질문**과, 같은 질문을 실제 사용자처럼 구어체로 바꿔 쓴 **다양한 형태 질문** 두 가지로 평가

| 방식 | 정제된 질문 Recall@5 | 다양한 형태 질문 Recall@5 | 다양한 형태 질문 MRR | 질문당 시간 |
| --- |--------------------------:|------------------------:|---------------:| ---: |
| base (벡터 검색) |                     0.333 |                   0.299 |          0.279 | 0.9초 |
| HyDE (LLM 가상 문장) |                     0.402 |                   0.379 |          0.340 | 2.4초 |
| Reranker (LLM 재정렬)\* |                     0.402 |                       — |              — | 2.4초 |
| HyDE + Reranker\* |                     0.448 |                       — |              — | 2.6초 |
| **Hybrid (벡터 + BM25)** |                 **0.609** |               **0.621** |      **0.502** | **0.9초** |
| HyDE + Hybrid |                     0.598 |                   0.621 |          0.489 | 2.4초 |

\* Reranker는 정제된 질문으로만 측정 (`experiments/results/exp_b_retrieval_20261116_1624`)

→ **Hybrid가 가장 정확하고 가장 빠릅니다.** HyDE · Reranker처럼 LLM을 더 쓰는 방식은 정확도 향상이 작고 질문당 1.5초가량 느려져, 서비스는 Hybrid 방식을 최종적으로 채택했습니다.

## 웹 서비스

1. **검색어 · 기간 입력** → 의미 고르기 (없으면 직접 입력)
2. **준비 과정 표시** — 수집 · 필터링 · 저장 진행 상황과 경과 시간
3. **최근 주요 이슈 Top 5** — 제목을 누르면 원문, 비슷한 기사 목록도 펼쳐 볼 수 있음
4. **질문하기** — DB에 저장된 기사가 있으면 **준비 중에도 바로 답하고**, 새 기사가 들어오면 이어서 답함. 답변마다 참고한 기사 시점을 표시

| DB 재사용 효과 | 이전 | 지금 |
| --- | ---: | ---: |
| 이미 찾아본 검색어로 질문 시작 | 약 13초 | **1.1초** |
| 같은 검색어 다시 준비 | 20.1초 | **5.2초** |

Google Cloud Run(서울)에 배포되어 있고, `main`에 merge하면 자동으로 다시 배포됩니다. 여러 사용자가 동시에 써도 됩니다.

## 시작하기

Python 3.11 / 3.12, gcloud CLI 필요

```bash
python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env                                # API 키 입력
gcloud auth application-default login               # Firestore 로그인 (본인 Google 계정)
gcloud auth application-default set-quota-project qupict
python admin.py init-db                             # 검색 인덱스 만들기 (처음 한 번)
python web.py                                       # http://127.0.0.1:8000
```

| 파일 | 용도 | 예시 |
| --- | --- | --- |
| `web.py` | 웹 서비스 | `python web.py --port 8080` |
| `run.py` | 터미널 서비스 | `python run.py 강남 30` |
| `admin.py` | DB 관리 | `collect 검색어` · `filter-all` · `index-all` · `status` |
| `evaluate.py` | 평가 | `exp-a` · `exp-b` · `sim` · `make-qa` |
| `tests/run_offline.py` | 오프라인 테스트 (API · DB 없이) | `python tests/run_offline.py` |
