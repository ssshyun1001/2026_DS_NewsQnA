## 프로젝트 개요

QuPicT는 사용자가 찾고 싶은 뉴스만을 근거로, 기사 본문과 사진 속 정보까지 참고하여 답을 제공하는 AI 뉴스 질의응답 서비스입니다. 기존 뉴스 검색은 동음이의어, 줄임말 등으로 인해 의도와 무관한 기사가 함께 검색되고, 사진으로 제공되는 표의 내용을 검색하기 어렵습니다. 또한, 중복 기사가 많아 정보를 찾는 과정에서 피로를 느낍니다.

본 프로젝트는 이와 같은 불편함을 해소하고자 **검색어 의미 구분, 뉴스 본문 및 사진 통합 분석, 주요 이슈 브리핑, 질의응답** 기능을 제공합니다.

- 검색어를 입력하면 검색어의 의미 후보를 제시하고, 기사를 수집한 뒤 선택한 의미와 무관한 기사를 걸러냅니다.
- OCR 기법으로 사진 내 정보를 읽어 답변에 반영합니다.
- 주요 이슈 브리핑을 정리하여 제공함으로써, 사용자가 질문의 방향을 잡도록 돕습니다.
- 사용자의 질문에 기사를 기반으로 답변하며, 제목과 원문 링크를 통해 출처를 직접 확인할 수 있습니다.

## 기획 의도

### 제작 배경

검색어가 동음이의어, 합성어, 줄임말인 경우에는 사용자가 원하는 단어의 의미와 상관없이 입력된 단어가 포함된 기사가 나열됩니다. 예를 들어 '서울여대'를 검색하면 서울여자대학교 기사와 함께 서울 지역의 여러 여자대학교에 관한 기사가 혼합되어 나오고, '눈'을 검색하면 날씨 기사와 신체 기관에 관한 기사가 구분 없이 검색됩니다. 결국 원하는 기사를 찾기 위해서는 사용자가 기사를 직접 확인해야 합니다.

이 밖에도 기사의 핵심 수치나 내용이 사진, 표, 인포그래픽 속 글자로만 제공되는 경우, 대부분의 서비스는 본문 텍스트만 다루기 때문에 이러한 정보를 반영하지 못합니다. 또 같은 사건을 여러 언론사가 비슷한 내용으로 보도하다 보니 사용자는 내용이 유사한 기사를 여러 번 읽게 됩니다. 대규모 언어 모델(LLM) 기반 질의응답 서비스 역시 최신 소식이 충분히 반영되지 않거나, 어느 시점의 어떤 자료를 근거로 답했는지 알기 어렵다는 한계가 있었습니다.

### 목적

QuPicT는 사용자가 원하는 뉴스 정보를 정확하고 효율적으로 얻을 수 있도록 하는 것을 목적으로 합니다. 검색어의 의미가 모호하거나 정보가 여러 기사와 사진에 흩어져 있어도, 사용자가 기사를 하나하나 확인하지 않고 필요한 답을 얻을 수 있는 뉴스 질의응답 서비스를 구현하고자 했습니다.

### 목표

1. **검색 의도에 맞는 기사 선별**: 동음이의어·합성어·줄임말 검색어에서도 사용자가 의도한 의미의 기사만 답변 근거로 사용한다.
2. **정보 활용 범위 확대**: 기사 본문뿐 아니라 사진 속 정보까지 답변에 반영한다.
3. **정보 탐색 부담 감소**: 수집된 기사의 주요 이슈를 먼저 제시해 중복 기사를 반복해서 읽는 부담을 줄이고, 최신 이슈에 대한 정보를 제공함으로써 질문의 출발점을 제공한다.
4. **신뢰할 수 있는 답변 제공**: 최신 기사에 근거해 답변하고 출처를 함께 제시해, 사용자가 답변을 직접 검증할 수 있게 한다.

### 활용 대상

- **일반 사용자**: 여러 기사를 일일이 읽지 않고도 최신 이슈를 빠르게 파악할 수 있습니다.
- **동향 모니터링이 필요한 사용자**: 특정 기업·인물·주제를 꾸준히 추적하며 변화를 확인할 수 있습니다.
- **대학생·연구자**: 과제나 연구에 필요한 뉴스 자료를 질문만으로 조사하고 정리할 수 있습니다.

## 프로젝트 내용

QuPicT는 **① 검색어 의미 구분 → ② 뉴스 수집 → ③ 중복 제거 및 관련성 필터링 → ④ 멀티모달 데이터 처리 → ⑤ 최근 이슈 브리핑 → ⑥ 근거 기반 질의응답** 단계로 동작합니다. 질의응답에 사용한 LLM은 `gemini-3.5-flash-lite`입니다.

```text
 검색어 "강남"
   │
   ▼
 ① 의미 구분        sense.py      LLM 의미 후보(1~3개, 정의 · 별칭 · 연관어) → 사용자 선택 / 직접 입력 (Firestore 캐시)
   │                               1. 방송인 강남  2. 지역 강남  …  / "기타" 직접 입력
   ▼
 ② 수집             collect.py    "검색어 + 연관어"·별칭으로 네이버 뉴스 동시 검색
   │                               → 본문 · 발행일 · 언론사 · 사진 · 캡션 수집 (DB에 있는 기사는 재사용)
   ▼
 ③ 중복 제거 ·      filtering.py  비슷한 기사를 대표 기사 하나로 묶음 (LLM 없음)
   │ 관련성 필터링                  → 1차 규칙 점수(연관어 − 배제어) → 2차 LLM 판정(관련/무관/보류 + 근거)
   ▼
 ④ 멀티모달 처리    indexing.py   본문 청크 + 사진 속 글자(OCR) → 임베딩(1536차원) → Firestore 벡터 DB
   │
   ├──▶ ⑤ 이슈 브리핑  hot.py      가장 많이 묶인 이슈 Top 5 + 기사 속 문장 그대로 요약 (LLM 없음)
   ▼
 ⑥ 질의응답         retrieval.py  하이브리드 검색(벡터 + BM25, RRF) → 상위 청크
                    qa.py          근거 인용 답변 + 기사 제목 · 원문 링크, 최근 대화 기억
```

### ① LLM 기반 검색어 의미 구분

사용자가 검색어를 입력하면, LLM이 가장 많이 사용되는 의미를 최소 1개에서 최대 3개까지 후보로 제시하며, 후보 중 원하는 의미가 없을 때는 사용자가 직접 입력할 수 있습니다. 각 후보에는 **정의, 별칭, 연관어**가 함께 생성되고, 선택되지 않은 의미의 연관어는 이후 단계에서 관련 없는 기사를 걸러내는 **배제어**로 사용됩니다. 생성된 의미 후보는 Firestore에 저장하여 같은 검색어에 대한 반복적인 LLM 호출을 줄이고, 매번 일관된 결과가 나오도록 구성하였습니다.

같은 검색어라도 **고른 의미에 따라 연관어와 배제어가 뒤바뀝니다.**

| 검색어 | 고른 의미 | 연관어 (찾을 단어) | 배제어 (걸러낼 단어) |
| --- | --- | --- | --- |
| 당근 | 당근마켓 | 중고거래, 동네생활, 당근페이, 직거래 | 농가, 수확, 당근즙, 레시피 |
| 당근 | 채소 당근 | 농가, 수확, 당근즙, 레시피 | 중고거래, 동네생활, 당근페이, 직거래 |
| 애플 | 기업 Apple | 아이폰, 맥북, 팀 쿡, iOS | 과수원, 농가, 사과값, 품종 |
| 애플 | 과일 사과 | 과수원, 농가, 사과값, 품종 | 아이폰, 맥북, 팀 쿡, iOS |

### ② 의미 기반 뉴스 검색 및 수집

선택된 의미의 별칭과 연관어를 조합해 여러 개의 검색어 후보를 만들고, 네이버 뉴스 API로 관련 기사를 수집합니다. 이후 BeautifulSoup 등을 이용해 기사 본문, 발행일, 언론사, 사진과 캡션 정보를 수집합니다. 기사는 URL을 기준으로 한 번만 저장되며, 하나의 기사가 여러 검색 주제와 연결될 수 있도록 데이터베이스를 설계하였습니다.

수집 시간을 줄이기 위해 병렬 처리를 적용하였습니다.
- 여러 검색어의 뉴스 검색 요청을 동시에 보내며, 비동기 방식으로 기사 페이지를 **최대 64건까지 동시에** 내려받습니다.
- 수집 시간의 대부분을 차지하던 본문 해석은 **여러 CPU 프로세스에 나누어** 처리해 시간을 단축했습니다.
- 이미 데이터베이스에 저장된 기사는 다시 수집하지 않고 재사용하여, 같은 검색어를 다시 검색할 때는 새로 발행된 기사만 수집합니다.

### ③ 중복 제거 및 관련성 필터링

내용이 같거나 매우 비슷한 기사는 하나로 묶어 중복을 제거합니다. 그다음 관련성은 두 차례에 걸쳐 판단합니다.

1. **규칙 기반 필터**: 선택한 의미의 연관어와 선택하지 않은 의미의 배제어를 활용해 관련성이 낮은 기사를 걸러냅니다.
2. **LLM 판정**: LLM이 기사 제목과 본문을 읽고 관련성을 판정합니다.

판정 시간을 줄이기 위해, 묶인 중복 기사는 따로 판정하지 않고 대표 기사의 판정을 그대로 적용하며, 규칙 필터로 분명히 무관한 기사를 먼저 걸러 LLM 호출 수를 줄였습니다. 또한 LLM에는 기사 8건을 묶어 한 번에 판정을 요청하고, 이 요청들을 병렬로 처리합니다.

필터링 성능을 객관적으로 검증하기 위해 **988건의 기사에 직접 정답 라벨**을 부여하였으며, 정밀도(Precision), 재현율(Recall), 그리고 두 지표를 종합한 F1 score로 성능을 평가하였습니다.
- **정밀도**: 필터를 통과한 기사 중 실제 관련 기사의 비율
- **재현율**: 실제 관련 기사 중 필터가 찾아낸 기사의 비율
- **F1 score**: 두 지표의 조화평균

정밀도가 낮아 무관한 기사가 섞이면, 동음이의어처럼 서로 다른 대상의 내용이 하나의 답변에 섞이거나 사용자의 관심과 무관한 이슈가 브리핑에 제시될 수 있습니다. 정밀도는 답변의 정확성과 서비스 신뢰도에 직접 영향을 주므로, 본 프로젝트는 정밀도를 주요 지표로 삼아 향상시키고자 하였습니다. 그 결과 재현율은 0.93으로 7.1%p 낮아졌지만, **정밀도를 0.41에서 0.59로 17.3%p 높였고, F1 score는 0.58에서 0.72로 13.4%p 향상**되었습니다 (아래 [실험 A](#실험-a--관련성-필터링)).

### ④ 멀티모달 데이터 처리 및 벡터 DB 구축

기사 본문은 검색에 적합한 크기로 분할하였고, 기사 사진은 광학 문자 인식(OCR) 기법으로 사진 내 정보를 인식·추출하여 텍스트 설명으로 변환합니다. 이를 통해 사진과 본문의 정보를 모두 참고하여 답변을 생성할 수 있습니다.

분할된 텍스트는 `text-embedding-3-small` 모델로 1536차원 벡터로 임베딩한 뒤 Google Cloud Firestore에 저장하였으며, Firestore의 벡터 검색(코사인 유사도)으로 질문과 의미가 가까운 정보를 찾습니다. 기사 원문, 사진 설명, 분할 본문, 임베딩 결과를 모두 저장해 두기 때문에 사용자가 검색한 내용에 대한 정보를 한 번에 모아 보여 줄 수 있습니다.

### ⑤ 검색어 관련 최근 주요 이슈 브리핑

중복 제거 과정에서 비슷한 기사들은 대표 기사 하나로 묶이는데, 묶인 기사가 많을수록 관련 뉴스가 많이 나오는 주요 이슈라고 판단했습니다. 이 묶음 크기를 기준으로 **상위 5개 이슈**를 선정해 보여 줍니다.

- 실제 기사 문장을 그대로 보여 주므로 내용이 왜곡될 염려가 없습니다.
- 새로 발행된 뉴스가 없으면 데이터베이스에 저장된 기사를 바탕으로, 같은 입력에는 같은 결과가 나옵니다.
- 제목을 눌러 원문으로 이동하거나, 함께 묶인 유사 기사 목록을 펼쳐 각각의 원문을 볼 수 있습니다.

수집된 기사 중 주목받는 핵심 이슈를 먼저 보여 줌으로써, 사용자가 무엇을 물어볼지 정하는 출발점 역할을 합니다.

### ⑥ RAG 기반 뉴스 질의응답

사용자가 선택한 주제에 대해 질문하면, 질문과 관련성이 높은 기사 내용을 **하이브리드 검색(Hybrid Search)** 으로 찾습니다.
- **벡터 검색**: 질문과 의미가 유사한 내용을 찾습니다.
- **BM25 키워드 검색**: 인물명, 기업명처럼 질문의 핵심 단어가 중요하게 등장하는 내용을 찾습니다.
- 두 검색 결과는 **RRF(Reciprocal Rank Fusion)** 알고리즘으로 하나의 순위로 통합합니다.

선정된 기사 내용을 LLM에 전달해 답변을 생성하며, 참고한 기사 제목과 원문 링크를 함께 제시해 사용자가 직접 출처를 확인할 수 있도록 설계하였습니다.

## 성과 및 기대효과

### 성과

필터링과 검색 방식을 여러 조합으로 비교 검증한 결과, 최종 제안한 방식이 기존 방식에 비해 뉴스 필터링 분류 성능과 검색 성능이 모두 향상되었습니다.

- **기사 필터링**: 필터링 적용 전 대비 재현율(Recall)은 0.93으로 7.1%p 낮아졌지만, 정밀도(Precision)를 0.41에서 0.59로 17.3%p 높였고, 그 결과 F1 score가 0.58에서 0.72로 13.4%p 향상되었습니다.
- **정보 검색**: 상위 5개 검색 결과 안에 정답 관련 정보가 포함되는 비율(Recall@5)이 29.9%에서 62.1%로 32.2%p 높아졌고, 정답이 얼마나 앞 순위에 나타나는지를 보여 주는 MRR도 0.279에서 0.502로 개선되었습니다.

이러한 개선은 서비스 품질에 큰 영향을 미치는 평균 검색 시간의 큰 증가 없이 이루어져, 정확도와 효율성을 함께 확보할 수 있었습니다. 완성된 서비스는 웹에 배포하여 누구나 바로 이용할 수 있습니다.

### 기대효과

- 사용자가 검색어 의미를 직접 고르면, 중복 제거와 2단계 관련성 필터링을 통해 의도와 무관한 정보가 섞여 생기는 불편함을 줄일 수 있습니다.
- 본문과 사진 정보를 함께 다루므로, 텍스트만으로는 찾기 어려웠던 정보까지 검색 범위가 넓어집니다.
- 최근 이슈 브리핑을 통해 여러 기사를 일일이 읽지 않아도 주제의 최신 흐름을 빠르게 파악할 수 있습니다.
- 수집·처리 결과를 데이터베이스에 저장해 재사용하므로 불필요한 API 호출이 줄고, 실험과 성능 개선도 효율적으로 진행할 수 있습니다.

## 성능 평가

모든 실험 결과는 `evalset/results/`, `experiments/results/`, `experiments/results_hyde_hybrid/`에 CSV·JSON으로 남아 있습니다.

### 실험 A — 관련성 필터링

`python evaluate.py exp-a` · 9개 topic(검색어 × 의미), **사람이 직접 라벨링한 기사 988건** 기준 (`evalset/labeled_set_*.json`).

| 방법 | Precision | Recall | F1 | LLM 호출 |
| --- | ---: | ---: | ---: | ---: |
| baseline (API 결과 그대로) | 0.412 | 1.000 | 0.584 | 0 |
| 1-a 별칭 포함 여부 | 0.439 | 0.963 | 0.604 | 0 |
| 1-b 검증 키워드 (이전 버전 방식)\* | 0.786 | 0.527 | 0.631 | 0 |
| 1-c 규칙 점수만 | 0.482 | 0.774 | 0.594 | 0 |
| 2-b LLM 판정만 | 0.578 | 0.953 | **0.720** | 126 |
| **제안 (규칙 → LLM)** | **0.585** | 0.929 | 0.718 | **115** |

\* 1-b는 검증 키워드를 정할 수 있는 topic(349건)만 평가. Precision은 높지만 관련 기사의 절반 가까이를 놓칩니다.

- 제안 방식은 Recall 0.93을 유지하면서 Precision을 **0.412 → 0.585**로 올렸고, 규칙 점수로 분명한 무관을 먼저 걸러 LLM만 쓸 때보다 호출 수가 적습니다 (126 → 115).
- 동음이의어가 뚜렷한 **방송인 강남**은 baseline Precision 0.105 → 제안 방식 **1.000** (F1 0.19 → 1.00).

### 실험 B — 검색 방식

팀 골든셋 118문항 중 수집된 **87문항** 기준. 질문 원문(`qa_set_hyde_hybrid.csv`)과, 같은 질문을 실제 사용자처럼 구어체로 바꿔 쓴 질문(`qa_set_hyde_hybrid_varied.csv`) 두 가지로 평가했습니다.

| 방식 | 하는 일 | Recall@5 (원문) | MRR (원문) | Recall@5 (구어체) | MRR (구어체) | 질문당 시간 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| base | 질문 그대로 벡터 검색 | 0.333 | 0.280 | 0.299 | 0.279 | 0.9초 |
| HyDE | LLM이 가상 기사 문장을 써서 벡터 검색 | 0.402 | 0.337 | 0.379 | 0.340 | 2.4초 |
| Reranker\* | 벡터 검색 후보를 LLM이 0~10점으로 다시 순위 매김 | 0.402 | 0.334 | — | — | 2.4초 |
| HyDE + Reranker\* | 위 둘을 같이 | 0.448 | 0.372 | — | — | 2.6초 |
| **Hybrid (최종)** | **벡터 검색 + BM25 키워드 검색, RRF로 합침** | **0.609** | **0.508** | **0.621** | **0.502** | **0.9초** |
| HyDE + Hybrid | 위 둘을 같이 | 0.598 | 0.501 | 0.621 | 0.489 | 2.4초 |

\* Reranker는 `experiments/results/exp_b_retrieval_20261116_1624` (원문 질문만, 같은 87문항)에서 가져온 값이고, 나머지는 `experiments/exp_b_hyde_hybrid.py` 결과입니다.

- **Hybrid가 가장 정확하고 가장 빠릅니다.** 구어체 질문 기준 Recall@5 0.299 → **0.621**, MRR 0.279 → **0.502**이고, 검색에 LLM을 쓰지 않아 시간은 base와 같습니다.
- HyDE · Reranker는 정확도가 조금 오르지만 LLM 호출 때문에 질문당 1.5초가량 느려지고, Hybrid에 HyDE를 더해도 나아지지 않습니다.
- 그래서 웹 · `run.py`는 **Hybrid만** 씁니다 (`qupict/retrieval.py`, `qupict/bm25.py`).

## 웹 서비스

**배포 주소: <https://qupict-920254012527.asia-northeast3.run.app/>** (Google Cloud Run, 서울 리전)

로컬에서 실행하려면:

```bash
python web.py           # http://127.0.0.1:8000 (--host · --port로 변경)
```

1. 검색어와 기간 입력 → 의미 고르기 (후보마다 정의 · 별칭 · 연관어 표시, 맨 아래 "기타 (직접 입력)")
2. 수집 · 중복 제거 · 판정 · 인덱싱 진행 상황을 로그로 표시 (줄마다 경과 시간, "DB 재사용 N건 + 새로 저장 M건")
3. **최근 주요 이슈 Top 5** — 비슷한 기사가 가장 많이 묶인 이슈 5건과 한 줄 요약 (LLM 없이 기사 속 문장 그대로). 따로 돌아서 질문을 막지 않음
4. 질문하기 — **준비와 동시에** 시작
   - 이 검색어 · 의미로 DB에 저장된 기사가 있으면 그 기사로 먼저 답하고, 준비가 끝나면 새 기사까지 넣어 이어서 답함 (앞 대화 유지)
   - 답변마다 **어느 시점의 기사를 참고했는지** 표시 ("○○까지 수집해 DB에 저장해 둔 기사를 참고한 답변입니다" / "○○에 새로 모은 기사까지 참고한 답변입니다")
   - 저장된 기사에 근거가 없으면 답하지 않고, 새 기사를 저장한 뒤 자동으로 다시 질문
   - 저장된 기사가 아예 없으면 준비가 끝난 뒤 답함

여러 사용자가 동시에 써도 서로 기다리지 않도록 작업 · 대화를 사용자별로 나누고, 같은 대상은 한 번만 준비합니다. 페이지를 나가면 그 사용자의 작업 · 대화는 서버 메모리에서 지웁니다.

DB 재사용으로 체감 속도가 크게 달라졌습니다.

| 상황 | 이전 | 지금 |
| --- | --- | --- |
| 이미 준비한 검색어로 질문 받기 시작 (방송인 강남) | 약 13초 | **1.1초** |
| 같은 검색어 다시 준비 (당근) | 20.1초 | **5.2초** |

Google Cloud Run 배포용 `Dockerfile`이 포함되어 있습니다 (Python 3.12, CPU판 torch로 이미지 크기 절감). GitHub `main`에 push하면 Cloud Run이 이 파일로 다시 빌드 · 배포합니다.

### 실행 파일 — 용도마다 하나

| 파일 | 대상 | 주요 명령 |
| --- | --- | --- |
| `web.py` | 서비스 (브라우저) | `python web.py [--host 0.0.0.0] [--port 8080]` |
| `run.py` | 서비스 (터미널) | `python run.py 강남 30` (검색어 · 기간) · `--max N`(최대 기사 수, 기본 100) · `--memory`(DB 없이 FAISS) · `--timing`(단계별 시간표) |

### DB 설계 요점

DB는 Google Cloud Firestore (서울 `asia-northeast3`, `(default)` DB)입니다. 컬렉션 구조는 `qupict/db.py` 맨 위 설명에 있습니다.

| 컬렉션 | 내용 |
| --- | --- |
| `query_senses` | 검색어별 의미 후보 캐시 (LLM 후보 + 직접 입력, 선택 횟수) |
| `topics` · `topic_keys` | 검색어 + 고른 의미, 배제어, 대조할 다른 의미 (번호는 `counters/topics`) |
| `articles` | 기사 본문·언론사·발행일·임베딩 + 사진(주소·캡션·OCR/설명, 파일은 저장 안 함). 문서 id = link 해시 — 여러 topic이 공유 |
| `article_topics` | topic별 판정(관련/무관/보류 + 근거), 중복 표시, 정답 라벨 |
| `chunks` | 청크 + 임베딩. `search_keys`(topic · 판정)와 발행일로 거른 뒤 벡터 검색(`find_nearest`, 코사인) |

- 기사는 한 번만 저장하고, **기간은 발행일 기준**으로 조회할 때 정합니다 → 같은 topic을 기간만 바꿔 재사용.
- 시스템 판정(`status`)과 사람의 정답(`label`)을 별도 필드로 두어 실험에서 직접 비교합니다.
